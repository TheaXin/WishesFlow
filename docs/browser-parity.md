状态：五页与共享 SQLite 表结构已实现；发布状态以 GitHub Actions 和线上页脚版本为准。下方 v1/v2 内容为返工历史，当前架构见 v3。

用户反馈：浏览器版草率，与 Streamlit + SQLite 对不上，功能界面未区分。
目标：保留本地版五个页面的职责与主要流程，在浏览器本地持久化约束下提供完整对应实现。既有线上版不能视作已完成的功能对齐版本。

## 实施约束

- 不修改或清空既有 wishflow.browser.v1 记录。新结构升级应保留原始备份，明确归属资料，迁移失败不能覆盖旧数据。
- 昵称属于本机资料区分，不作身份认证或隐私保护承诺。
- 保持 product-site 产品介绍与 app 实际应用的边界；介绍页不得宣称尚未实现的功能。
- 使用共同业务样例核对 Python SQLite 与 JavaScript 的结果，避免只写各自都能通过的孤立测试。
- 不凭测试数量认定完整；需要逐页实际操作、刷新/资料切换、历史日期、空状态、重复操作、存储失败、导入失败及升级迁移验证。
- 布局检验：桌面侧栏与390px手机导航，键盘可用、无横向溢出；逐页截图检查。
- 测试通过后发布同仓库 main，等待 GitHub 测试与部署成功，核对线上 build.json 与源码 commit。

## v2 历史实现差异（v3 已替换存储层）

SQLite 与 localStorage 存储方式不同，均没有认证或跨设备同步。浏览器版多了备份页、心愿状态筛选、趋势数据表和近期记录；Streamlit 版使用自己的图表与控件。两版新金额均限制为正数、最多一亿元和两位小数。本地SQLite仍保留REAL字段，读取汇总和解锁比较采用十进制精确运算，不改写历史行；浏览器按整数分计算。两版金额均显示两位小数。旧数据无解锁时间时不伪造时间，后续新解锁会记录时间。v2 不新增本地版也没有的删除/改价功能。


## SQLite 逐操作验证

`tests/test_browser_sqlite_differential.py` 直接调用生产 `db/db.py`，并驱动 `tests/browser_oracle.cjs` 同时调用浏览器核心和实际 WebAssembly SQLite 适配器。每步额外核对实际 SQL 的接受/拒绝、逐条记录与金额汇总。每一步比较两端接受/拒绝、来源字段、打卡日期与金额、心愿排序/状态、余额、趋势和数量。覆盖固定种子随机序列、两昵称交叉操作、重复打卡、金额恰好够用、非法精度/优先级/未来日期等边界；不是分别对一个预期余额做断言。

该测试实际发现过 `0.10 + 0.70` 在SQLite浮点比较中小于 `0.80` 的问题，已修正本地汇总和解锁计算，保留回归用例。随机序列每一步都必须匹配，才允许发布。

当前项目实际 `db/wishflow.sqlite3` 已只读检查：完整性正常，五张业务表均0行。此事实不能证明另一份历史数据库的记录已迁移；网站与SQLite不自动同步。若用户有另一份实际数据，应先确认来源，再验证逐条记录，不把示例数据当作其真实数据。

原生页面验收 `tests/streamlit_smoke.py` 使用隔离SQLite和隔离Streamlit配置，验证同名收入来源不被覆盖、0.01元输入、0.80元精确显示及刚好够用的解锁/实现。该检查纳入CI，而非只验证浏览器页面。


## v3 真正 SQLite

用户明确要求浏览器也直接使用 SQLite，并全部保持一致。v3 使用 sql.js WebAssembly 实际运行 SQLite，IndexedDB 保存数据库二进制，Web Locks 串行化多标签写入。业务数据不再以JSON数组作为存储源。两端直接读取同一份 schema.sql，导入还比较列、类型、默认值、主键、外键和索引。

SQLite 文件可以在 Python 本地版与浏览器之间双向交换；替换导入之前校验文件和用户归属并要求确认。旧v1/v2仅作为迁移输入，原始存储保留。新写入按分校验计算，不修改迁移前业务金额。空昵称属于浏览器界面偏好，导出的 SQLite 文件包含实际业务记录，与本地数据库含义一致。

验证分层：原有逐操作差分；Python→WebAssembly→Python→WebAssembly文件往返；真实IndexedDB/刷新/Web Locks；五页实际数据库导出、取消导入、恢复、损坏及写入失败保护。引擎JS、WASM及MIT许可在仓库固定托管并检查哈希。CI 对以上检查全部通过后才发布；实际线上版本须与 build.json 及源码 commit 核对。
